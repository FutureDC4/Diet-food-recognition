# 上位机说明（可视化版）

> 图形界面的膳食识别系统：上传一张餐盘照片 → 识别菜品 → 估算重量与热量 →
> 按「餐次配额 + 结构评估」给出这一餐的判断与补充建议 → 本地 Ollama 组织成自然语言。

启动方式：双击 `启动上位机.bat`，或

```bash
py -3.10 上位机.py
```

---

## 1. 为什么要做单餐而不是算一天

从一张照片只能看到**一餐**。用一餐的热量去比「一天该吃多少」，结论很容易失真：
午餐吃了 700 kcal，可能是「太少」也可能是「刚好」，取决于这个人今天还吃了什么。

所以这里改成两件事并行：

| 逻辑 | 做法 | 解决什么问题 |
|---|---|---|
| **B. 单餐配额** | 把每日需求按餐次切开，得到这一餐的合理区间 | 这一餐吃多了还是吃少了 |
| **C. 结构评估** | 不看总量，看蛋白/纤维/蔬菜/主食/脂肪/钠的配比 | 这一餐吃得对不对 |

两者合起来才是完整判断：**在配额内、结构合理** 才算好的一餐。
只做 B 会漏掉「热量刚好但全是油炸」；只做 C 会漏掉「结构不错但吃了两倍量」。

## 2. B：餐次配额的算法

### 2.1 能量预算

```
每日总消耗 TDEE  = BMR(Mifflin-St Jeor) × 活动系数
本餐预算         = TDEE × 餐次占比
合理区间         = 本餐预算 × (0.9 ~ 1.1)
```

餐次占比（`data/dri_cn.yaml` → `meal_share`）：

| 餐次 | 占比 | 说明 |
|---|---|---|
| 早餐 | 25% | |
| 午餐 | 40% | |
| 晚餐 | 35% | |
| 加餐 | 10% | 不额外占一天的能量，从午、晚各匀 5% |

三餐加起来正好 100%，**不做归一化**——否则午餐会被压到 36%，和「午餐按 40% 算」对不上。

示例：TDEE 2556 kcal 的人，午餐预算 1022 kcal，合理区间 **920-1124 kcal**。

### 2.2 营养素目标

| 项目 | 每日推荐 | 折算到午餐（40%） | 依据 |
|---|---|---|---|
| 蛋白质 | 65 g（男）/ 55 g（女），且不低于 1.0 g/kg | 26 g | DRIs 2023 RNI + 体重法取大值 |
| 膳食纤维 | 25 g | 10 g | DRIs 2023 AI |
| 蔬菜 | 400 g（指南 300-500 的中位） | 160 g | 膳食指南 2022 |
| 钠 | < 2000 mg（≈5 g 盐） | ≤ 667 mg | 膳食指南 2022 |
| 主食供能比 | — | 25%-55% | 单餐经验阈值 |
| 脂肪供能比 | 20%-30% | 同 | DRIs 2023 |

蛋白质取「RNI 按餐次分摊」与「体重 × 1.0 g/kg」的**较大值**：
前者照顾矮小/轻体重人群，后者照顾健身人群，避免任一口径太偏。

## 3. C：结构评估的 8 个检查项

每项都会给出「实际值 / 参考值 / 判断（达标·偏低·偏高·需控制）/ 一句话解释」。

| 检查项 | 怎么算 | 偏低 | 偏高 |
|---|---|---|---|
| 本餐热量 | 总热量 vs 预算区间 | 可能吃不饱或漏识别 | 注意烹调油与主食量 |
| 蛋白质 | 总蛋白 vs 目标 | <80% 目标记偏低 | — |
| 膳食纤维 | 总纤维 vs 目标 | <90% 目标记偏低 | — |
| 蔬菜占比 | 蔬菜重量 / 总重量 | <30% | — |
| 主食供能比 | 主食热量 / 总热量 | — | >55% |
| 脂肪供能比 | 脂肪 ×9 / 总热量 | <20% | >30% |
| 钠 | 总钠 vs 667 mg | — | >667 mg |
| 促炎负荷 | 油炸+加工肉热量 / 总热量 | — | >30% |

最后给出一个「达标 x/8」的分数，用于一眼判断这餐的整体质量。

**菜品的归类**来自营养表里的 `category` 字段（主食/蔬菜/荤菜/油炸/加工肉/奶类/水果/甜点），
`risk` 字段标记油炸与加工肉，用于计算促炎负荷。

## 4. 「该加什么」——规则生成，不依赖大模型

这一层的输出是**可直接执行的动作**，每条包含食物名 + 分量 + 能补多少：

```
＋ 加一份 150g 清炒时蔬或白灼菜（约 +2.2g 纤维），把这一餐蔬菜补到 210g
＋ 加 300ml 牛奶或无糖酸奶（+310mg 钙，约占全天推荐量 40%）
－ 炸鸡排这类一周控制在 1-2 次，下次换成清蒸、白灼或炖的做法
－ 这餐偏咸，下一餐少放酱油/少吃腌制食品，多喝一杯水
```

触发条件（按优先级）：

| 缺口 | 触发 | 给什么 |
|---|---|---|
| 蛋白质差 ≥ 18 g | 加豆腐/鸡胸 | 150 g 豆腐 或 100 g 鸡胸 |
| 蛋白质差 8-18 g | 加蛋/酸奶 | 1 个水煮蛋 或 200 ml 无糖酸奶 |
| 蔬菜差 ≥ 60 g | 加蔬菜 | 100-300 g 清炒时蔬（按缺口取整到 50 g） |
| 纤维不足但蔬菜够 | 换主食 | 杂粮饭 / 蒸红薯替代一半 |
| 主食供能 > 55% | 减主食 | 减 25% 的主食重量 |
| 油炸/加工肉 > 30% | 换做法 | 清蒸 / 白灼 / 炖 |
| 钠 > 667 mg | 下餐清淡 | 少酱油、少腌制 |
| 钙 < 25% 目标 | 补奶 | 300 ml 牛奶 |
| 维 C 与铁同时低 | 一起补 | 橙子/猕猴桃（维 C 促进铁吸收） |

## 5. 米饭三级处理

米饭在中餐里最容易被菜压住，检测框只框到露出来的那一角，导致主食热量被严重低估。
所以按「米饭框面积 / 全部食物面积」分三级：

| 级别 | 面积占比 | 处理 |
|---|---|---|
| 一级 | ≥ 20% | 框够大，**直接用检测值** |
| 二级 | 4% ~ 20% | 被遮挡，按「占食物总面积 1/3」反推面积 |
| 三级 | < 4% | 正常人不会只打这么一点饭，**判为误检，直接剔除** |

二级的反推公式（设其他菜面积和 O，米饭面积 R）：

```
R / (R + O) = 1/3   =>   R = O / 2
```

即「米饭面积 = 其余菜面积之和的一半」，修正后米饭正好占食物总面积的 1/3。
修正后还要过一道单份上限（`weight_estimation.rice_rule_max_g`，默认 250 g）：
因为其他菜的标注框本身偏大，反推出的米饭面积会跟着放大，不限制会算出 400 g 一碗饭。

阈值可在 `config.yaml` 里调：

```yaml
rice_rule:
  enabled: true
  trust_ratio: 0.20      # ≥ 20% 可信
  target_ratio: 0.3333   # 被遮挡时修正到的目标占比
  reject_ratio: 0.04     # < 4% 判为误检
```

## 6. 食物高度档位

单张照片是二维的，看不出这一格菜堆了多高。而重量 = 面积 × 高度 × 密度，
高度猜错 30%，重量就错 30%。

所以界面上给了三个档位，把系数乘在「按食物类型查到的默认高度」上：

| 档位 | 系数 | 适用 |
|---|---|---|
| 薄摊 | 0.75 | 平盘摊开、汤菜、凉拌 |
| 常规 | 1.00 | 食堂一格菜的正常高度（默认） |
| 堆高 | 1.35 | 大份、堆起来的一盘 |

结果页底部会写明本次用的是哪个档位，提示词和导出报告里也会带上，
保证「重量是怎么来的」可追溯。

## 7. 营养数据：来源与字段

`data/food_reference.yaml` 里每一类食物都是**成品典型值 / 100 g 可食部**：

| 字段 | 含义 |
|---|---|
| `calories_per_100g` | 热量 kcal |
| `protein_g` / `fat_g` / `carb_g` | 三大营养素 g（**实测值**，不再由热量反推） |
| `fiber_g` | 膳食纤维 g |
| `sodium_mg` | 钠 mg（含烹调盐，判断「咸不咸」的关键） |
| `density` | 密度 g/cm³（体积 → 重量） |
| `category` | 主食 / 蔬菜 / 荤菜 / 油炸 / 加工肉 / 奶类 / 水果 / 甜点 |
| `cooking` | 蒸 / 煮 / 清炒 / 油炸 / 煎 / 干煸 / 炖 / 凉拌 |
| `inflammation` | 促炎倾向 低 / 中 / 高（依据烹调方式与加工度） |
| `micro` | 11 项微量元素，见下 |
| `note` | 一句话要点，生成建议时引用 |

微量元素（`micro`）：钙、铁、锌、硒、钾、镁、维生素 A、B1、B2、C、E。

**数据来源**

1. 《中国食物成分表》标准版第 6 版（杨月欣 主编，北京大学医学出版社）—— 主要依据
2. USDA FoodData Central —— 西式与油炸类对照
3. 《中国居民膳食指南（2022）》《中国居民膳食营养素参考摄入量（2023 版）》—— 判断阈值

**必须说明的局限**：数值是典型值，同一道菜因用油量、勾芡、含汤量不同，实际可有 ±20% 波动。
这套系统做的是「估算 + 趋势判断」，不是医学营养处方。报告末尾也标注了这一点。

### 7.1 装盘量 → 入口量（`app/calibration.py`）

估重算出来的是**装进盘子**的量，营养表描述的是每 100 g 食物本身。两者之间差三笔，
方向一致，都让结果偏高：

| 偏差 | 系数 | 取值依据 |
|---|---|---|
| 菜帮 / 果皮 / 骨 / 盘底汤汁吃不到 | `edible_ratio`（按 `category`） | 叶菜 0.88、荤菜 0.94、油炸 0.95、加工肉 0.97、主食 0.97 |
| 营养表含全部烹调油，浮油留盘底 | `oil.added × oil.residue`（按 `cooking`） | 清炒 0.70×0.32、煎 0.62×0.30、油炸 0.55×0.25、炖 0.45×0.22、蒸 0.10×0.05 |
| 盐 / 酱油溶在汤汁里 | `sodium_retention` | 0.78 |

计算顺序：先在装盘口径上扣掉「不入口的浮油」（`fat1 = fat0 × (1 − added × residue)`，
热量同步减去 `(fat0 − fat1) × 9`）与「随汤汁流失的盐」，再整体乘可食部比例。
蛋白、碳水、纤维、微量元素的装盘值相同，因此只乘 `edible_ratio`。

**方向校验**：100 g 清炒白菜脂肪保留 69%（表面浮油最多），100 g 蒸腊肠保留 96%
（油在肉里，不在表面）。这个方向比数值本身更重要——如果蒸煮类也被大幅扣油，说明参数配错了。

**可追溯**：每道菜同时保留 `gross_weight_g` / `gross_fat_g` / `gross_sodium_mg` / `gross_calories`，
分析结果里有 `calibration` 汇总块（before / after），报告与调参都用得上。
`nutrition_calibration.enabled: false` 可整体关闭，回到原始值。

**它的边界**：这一层只去掉「估算放大」的部分，不修饰真实结论。像腊肠 + 煎蛋 + 油炸薯饼
这类组合，扣掉全部浮油后脂肪供能仍在 55% 上下——那是食物构成决定的，系统应当把它报出来。

## 8. 微量元素与 DRIs

`data/dri_cn.yaml` 存的是中国居民 DRIs（2023 版）的 RNI/AI 值，按性别与年龄段取：

```yaml
micronutrients:
  calcium_mg: {name: 钙, rni: 800, unit: mg, ul: 2000}
  iron_mg:    {name: 铁, rni: 12,  unit: mg, ul: 42}   # 女性 18-49 岁 18 mg
```

按餐次折算后（钙 800 × 40% = 320 mg/餐），与本餐实际摄入比较，标出完成度最低的几项。

**只做方向提示，不做定量结论**，原因有两个：

- 单餐只占一天的一部分，天然「不达标」，把正常现象报成问题会误导；
- 碘和维生素 D 无法从菜品成分表估算（碘主要来自碘盐，维 D 主要靠日照），
  这两项在表里标了 `tracked: false`，不参与缺口计算。

## 9. 建议是怎么生成的（两层）

这是本系统最关键的一个设计决定：

```
规则层（app/diet_rules.py）        →  所有数值判断、分数、缺口、"该加什么"
     ↓  结构化结论
语言层（本地 Ollama，qwen2.5:1.5b） →  解释原因、组织成四节自然语言
```

**为什么不让大模型自己算**：本机跑的是 1.5B 模型 + CPU 推理，让它做
「目标 26 g、实际 18 g，还差多少」这类减法，错误率相当高；
更常见的是把「膳食纤维偏低」复述成「纤维达标」「纤维偏高」。

所以 prompt 里把结论**写死**，并要求第一节第一句原样使用规则层生成的总评：

```
【已判定的结论——必须原样采用，不许改判】
总评：热量偏高（1444 kcal，建议 934-1142）；膳食纤维、蔬菜占比和主食供能比不足；
      脂肪供能比、钠偏高；促炎负荷需要控制。
```

模型只负责解释「长期高钠与血压、油炸与炎症、纤维不足与肠道」这类因果，以及把
「加一份 150g 清炒时蔬」变成自然的一句话。这样既保证事实正确，又保留语言的自然度。

如果 Ollama 没启动，界面仍会显示规则层算出的配额、结构评估和「该加什么」，
只是少了 AI 那一段文字——**核心结论不依赖大模型**。

│              │  │                  │  蛋白 ████   65 g      │      │
│ 食物照片      │  └──────────────────┴───────────────────────┘      │

- **「历史记录」页**：按用户查当日汇总（几餐、合计热量、蛋白质）

用户档案存在 `data/users.json`，下次打开自动选中上次的用户，不用重复填身体信息。

## 12. 参数都在哪里

| 想改什么 | 改哪里 |
|---|---|
| 餐次占比、蛋白质/纤维/钠目标 | `data/dri_cn.yaml` |
| 某种食物的营养值、分类、烹调方式 | `data/food_reference.yaml` |
| 米饭三级阈值、单份上限 | `config.yaml` → `rice_rule` / `weight_estimation` |
| 高度档位系数 | `config.yaml` → `height_levels` |
| 各项食物默认高度、密度 | `config.yaml` → `weight_estimation.height_by_food` |
| Ollama 模型、温度、是否用 GPU | `config.yaml` → `ollama` |
| 结构评估阈值 | `data/dri_cn.yaml` → `structure` |
| 可食部比例、浮油与盐的折算力度 | `config.yaml` → `nutrition_calibration` |

改完不需要改代码，重启上位机即可生效（`dri_cn.yaml` 与 `food_reference.yaml` 每次启动读取）。

### 模型批量实测（方案C vs 基线，16 张 test 图）

`tools/test_plan_c.py` 走的是上位机同一条链路（检测 → 米饭三级 → 估重 → 结构评估），
只是把权重换成指定的 `.pt`，所以数字能直接对应界面里看到的结果。

| | 框级召回 | 精确 | F1 | 菜品级命中 |
|---|---|---|---|---|
| 方案C（Neck-CBAM + WIoU） | **71.4%** | 88.2% | **78.9%** | **86.0%**（49/57） |
| 基线（yolo11s + CIoU） | 55.6% | **89.7%** | 68.6% | 66.7%（38/57） |

- 「框级」按 IoU ≥ 0.5 且类别一致逐实例算；「菜品级」只看这盘菜有没有被认出来
  （同类多份会被合并成一个框，逐实例算会低估）。
- 方案C 的主要优势是**少漏菜**：16 张图里多认出 11 个菜品类别，
  典型如 `img_96`（5/5 vs 基线 2/5）、`img_143`（4/4 vs 2/4）。
- 两边共同的弱点：`carrot_eggs` 基本认不出（3 张全漏）；
  `triangle_hash_brown` 的单独特写会被判成 `fried_chicken_legs`（0.85 置信度），两个模型都错。
- 底盘（托盘）大合照里两模型都只认出 2-3 个菜，属于训练数据的场景缺口。

### 检测区域：为什么改成整图

同一批 25 张图对比「盘内裁剪后检测」与「整图检测」：

| 路径 | 框级召回 | 精确 | 命中框面积/真值（中位数） |
|---|---|---|---|
| 盘子 OBB 旋转裁剪 | 51.4% | 60.3% | 1.38 |
| 整图 | **77.0%** | **82.6%** | 1.31 |

裁剪图经过旋转，模型会给出更大的框，且盘边食物被切掉；训练与评估都在整图上做。
所以现在盘子只负责换算 px/cm，检测吃整图，由 `config.yaml → plate.crop_for_detection` 控制。

> 顺带修了一个坐标 bug：盘内裁剪时检测框是裁剪图坐标系，之前直接画在原图上，
> 框会整体偏移。现在 `FoodDetector` 用逆透视矩阵把框映射回原图，
> 估重仍用裁剪图上的真实像素面积，不受影响。
