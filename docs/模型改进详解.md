# 模型改进详解：CBAM + WIoU

> **状态：已完成训练与消融实验（2026-11）**
> 在自建 18 类中餐数据集上完成三组对比训练，最终采用 **方案 B（Neck 端 CBAM + WIoU v3）** 作为部署模型。
> test 集 mAP@0.5 **76.13%**（基线 74.63%，+1.50），Recall **73.13%**（基线 68.47%，**+4.66**）。

---

## 1. 为什么改

中餐「一盘多菜」场景的两个真实痛点：

| 痛点 | 现象 | 对应改进 |
|---|---|---|
| 背景干扰 | 盘边花纹、桌布、筷子、汤汁反光被误检 / 抢占注意力 | **CBAM**：通道+空间双注意力，压制背景、突出食物主体 |
| 小目标与重叠 | 一盘多菜时，小份菜（一勺青菜、几片香肠）框不准，低质量样本梯度淹没有效梯度 | **WIoU**：动态非单调聚焦，自动降权离群样本 |

早期用 COCO-80 权重时，类别形态差异大、背景单一，改进收益有限。换成中餐 18 类自建数据集后，
「多菜同盘 + 菜色相近 + 盘边干扰多」才真正成为瓶颈，改进的价值才体现出来。

---

## 2. CBAM 的两种插入位置（一败一成）

CBAM 放在哪里，对结果影响极大。项目实测了两种位置，结论相反。

### 2.1 方案 A：替换 backbone 末端的 C2PSA（❌ 效果变差）

```
backbone:
  - [-1, 1, SPPF, [1024, 5]]     # 9
  - [-1, 1, CBAM, [512]]         # 10  ← 原为 [-1, 2, C2PSA, [1024]]
```

文件：`models/yolo11s-cbam.yaml`

**思路**：C2PSA 偏全局位置建模、参数多（1024 通道时约 2.6 M），CBAM 更轻（约 0.26 M），
在「食物主体占据画面中心」的场景里属于用更小代价达到同等效果。

**实测结果：失败**。test mAP@0.5 从 74.63% 掉到 **70.54%（-4.09）**，mAP@0.5:0.95 从 50.24% 掉到 45.92%。

**原因分析**：C2PSA 位于 backbone 最末端（SPPF 之后），承担的是「全局位置建模」职责，
换成 CBAM 后破坏了预训练权重的深层特征分布；且 CBAM 的 sigmoid 门控在深层会削弱
已经高度抽象的语义特征，150 epoch 不足以重新收敛。

### 2.2 方案 B：Neck 输出端插入（✅ 效果最好，最终部署）

```
  - [16, 1, CBAM, [128, 8]]              # 23  ← 新增，P3 分支注意力
  - [19, 1, CBAM, [256, 8]]              # 24  ← 新增，P4 分支注意力
  - [[23, 24, 22], 1, Detect, [nc]]      # 25  Detect(P3+CBAM, P4+CBAM, P5)
```

文件：`models/yolo11s-cbam-neck.yaml`

**设计要点**：

1. **backbone 完全不动**：第 10 层 C2PSA 原样保留；
2. **在送进 Detect 前插两个 CBAM**：P3（第 16 层，128 通道）和 P4（第 19 层，256 通道）各一个；
3. **层 0~22 索引与原生 yolo11s 完全一致** → `yolo11s.pt` 权重可全量迁移，
   只有新增的 23/24 层和后移的 Detect(25) 随机初始化；
4. **CBAM 只喂给 Detect**，不参与 neck 内部信息传递，主路完全不受影响。

**为什么这样更有效**：P3/P4 是检测小/中目标的分支，中餐里「一勺菜、几片香肠」这类
小份菜正落在这一层。在这里做通道+空间注意力，直接提升小目标特征的信噪比，
而不破坏 backbone 的通用特征提取能力。

### 2.3 通道数为什么写死

`parse_model` 对未知自定义模块走 `else: c2 = ch[f]`，**args 原样传入、不做 width 缩放**，
必须手写「缩放后」的实际通道数：

| 分支 | 计算 | yolo11s 写 | n | m / l / x |
|---|---|---|---|---|
| P3 | `min(256, 1024) × 0.5` | `[128, 8]` | `[64, 8]` | `[256, 8]` |
| P4 | `min(512, 1024) × 0.5` | `[256, 8]` | `[128, 8]` | `[512, 8]` |

第二个参数是 `reduction`，实测用 **8** 比默认 16 好（16 压得太狠，通道信息损失过多）。

### 2.4 为什么不用 SE / ECA

SE 只有通道维、ECA 只用 1D 卷积，都缺少空间维抑制；本场景「盘边 + 餐具 + 多菜边界」的干扰
主要在空间维，因此选 CBAM（通道 + 空间双注意力）。

## 3. WIoU 替代 CIoU

### 3.1 接入方式：猴补丁，不改 site-packages

文件：`models/wiou_patch.py`

```python
import models                                    # 触发 CBAM 注册
from models.wiou_patch import apply_wiou
apply_wiou("v3", warmup_steps=300)               # 前 300 步用 CIoU 热身
```

原理：
- `BboxLoss.__init__` —— 额外挂一个 `WIoULoss` 实例
- `BboxLoss.forward` —— IoU 项换成 WIoU，DFL 项保持官方实现
- `v8DetectionLoss` 内部是 `self.bbox_loss = BboxLoss(reg_max)`，补丁打在类上，
  任何新建的损失实例都会自动用 WIoU

训练脚本已封装：`py -3.10 tools/train_chinese.py --wiou v3`

### 3.2 公式与三档版本

- `L_IoU = 1 - IoU`
- `R_WIoU = exp( ρ² / (W_g² + H_g²) )`：ρ² 为预测框与真值框中心距平方，`W_g/H_g` 为最小外接框宽高。
  该项**尺度不变**，实现中做了 **梯度分离**（`detach`），避免距离项产生「把框拉大」的捷径梯度。
- 动态聚焦权重 `r`：
  - v1（`monotonous=None`）：`r = 1`，即 `L = R_WIoU · L_IoU`
  - v2（`monotonous=True`）：`r = sqrt(β)`，单调聚焦
  - **v3（`monotonous=False`，本项目采用）**：`r = β / (δ·γ^(β-δ))`，β 超过 δ 后权重迅速下降，形成非单调聚焦
  - 其中 `β = L_IoU / mean(L_IoU)`，`mean` 用 7000 步 EMA 估计，`γ=1.9, δ=3.0`

### 3.3 为什么比 CIoU 好

CIoU 对每个框「等权」；一旦某批里混进标注粗糙/遮挡严重的离群框，它的巨大梯度会把整批训练带偏。
WIoU 把「离群程度」写进权重，相当于**自动做难例挖掘 + 噪声抑制**，在噪声标注数据集上尤其明显。

中餐数据集标注的固有噪声（遮挡菜品只画露出部分、边界模糊）正好是这个机制的目标。

## 5. 消融实验结果（test 集，18 类）

| 实验 | 结构 | BBox Loss | Precision | Recall | mAP@0.5 | mAP@0.5:0.95 | 训练耗时 |
|---|---|---|---|---|---|---|---|
| **A（基线）** | yolo11s | CIoU | 75.76% | 68.47% | 74.63% | **50.24%** | 4260 s |
| **B（方案 A）** | yolo11s + CBAM（替换 C2PSA） | WIoU v3 | 73.29% | 67.02% | 70.54% | 45.92% | 5569 s |
| **C（方案 B）** ⭐ | yolo11s + CBAM（Neck P3/P4） | WIoU v3 | 74.66% | **73.13%** | **76.13%** | 48.43% | 6221 s |

### 判读

| 结论 | 依据 |
|---|---|
| ✅ **方案 B（Neck 端）有效** | mAP@0.5 **+1.50**、Recall **+4.66**，且 Recall 提升幅度远大于 mAP，说明主要收益在「少漏检」 |
| ❌ **方案 A（替换 C2PSA）有害** | mAP@0.5 **-4.09**、mAP@0.5:0.95 **-4.32**，破坏 backbone 深层语义特征 |
| ⚠️ **mAP@0.5:0.95 略降** | 方案 B 为 48.43%（基线 50.24%，-1.81），说明高 IoU 阈值下的定位精度略有牺牲 |
| ✅ **业务侧交叉验证** | 16 张 test 图菜品级命中率 **86.0%**（方案 B）vs **66.7%**（基线） |

**为什么接受 mAP@0.5:0.95 的下降**：

本项目最终产出是「这盘菜有什么、多少克、多少热量」。漏检一道菜 → 该菜重量和热量直接为 0，
整餐营养统计失真；而框定位误差 ±5% IoU 对面积估算的影响远小于重量估计本身的 ±30%~50% 误差。
因此**召回优先于高 IoU 定位精度**，方案 B 是正确的取舍。

## 6. 与当前系统的关系（部署状态）

**当前部署的是方案 B 模型**：

```yaml
# config.yaml
paths:
  food_model: models/weights/chinese_food_cbam_neck.pt
```

- **推理侧**：`src/detection/*.py` 顶部已有 `import models  # noqa`，
  ultralytics 能正确解析 CBAM 自定义层，开箱可用。
- **WIoU 只影响训练**，推理完全无感（`.pt` 里保存的是训练好的权重，不含损失函数）。
- **切回基线**：把 `config.yaml` 的 `food_model` 改成 `models/weights/chinese_food.pt`，代码零改动。

**换更大规模（m/l/x）时注意**：`yolo11s-cbam-neck.yaml` 的 `scales` 行和 CBAM 的通道数都要同步改，
参照 §2.3 的表格。
